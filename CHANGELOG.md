# Changelog

All notable changes to CMSIS Developer Assistant will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/), and this project adheres to [Semantic Versioning](https://semver.org/).

## [2.7.0] - 2026-10-28

The knowledge engine, with a core index in the extension and knowledge that packs ship, and more of the CMSIS Solution extension: its catalog of boards, devices and examples, project creation from an example, pack installation, and the rebuild, clean and stop actions. A pre-release.

### Added
- **`cmsis_action activate_environment`: the Arm Tools Environment Manager's Reactivate Environment for the agent (tester feedback).** A tester's first build on Windows waited 7 minutes for the environment prompt, and a build on this Mac failed four times with "CMake 3.27 or higher is required" after `vcpkg-configuration.json` had changed, because no tool could activate the environment or tell whether it had happened. `activate_environment` issues `environment-manager.reactivate` with the Uri of the manifest, as the Explorer's context menu does (without it the command fails, "Cannot read properties of undefined (reading 'fsPath')", which a Kimi Code run of the eval found), waits until CMSIS Solution rewrote `.cmsis/tools-environment.yml` and lists the tools it names; `running` while tools download or a prompt waits for the user. Every task action compares the manifest with that record first: a manifest newer than the record, or a missing record, puts one sentence before the result naming `activate_environment`.
- **`cmsis_action refresh`: CMSIS Solution's Refresh (Update RTE) for the agent (tester feedback).** A build failed with `file '…/RTX_Config.c' not found; use --update-rte`, no tool ran the panel's Refresh, and a tester's agent operated VS Code's command palette through screen control to get there. `refresh` issues `cmsis-csolution.refresh` — in CMSIS Solution 1.72.0 a convert with the RTE update, which writes the files a component brings — waits until csolution rewrote `<name>.cbuild-idx.yml` and answers ✅ or ❌ with the messages recorded there, or `running` while packs still load. A failed build whose csolution errors ask for `--update-rte` names `refresh` in its hint. `tools/list` grows by one enum word and one sentence, and three sentences of the `cmsis_action` description are shorter to keep it within 700 characters (surface snapshot updated); the guide's action table, the shell-to-tool table of the tool contract (`cbuild … --update-rte`), the user guide and the handler page follow.
- **The knowledge index is mandatory and ships with the extension.** The knowledge tools are always on; the core index is `resources/knowledge/core.db` (procedures, the error catalog, the documentation of Apache, MIT and BSD sources, reviewed issue digests). `knowledge.indexPath` replaces it for testing; `knowledge.enabled` and `knowledge.replaceSkills` are removed.
- **One installed skill, `cmsis-help`.** It is the health check (session, debug windows, recent problems) and the router to the debug topics and the knowledge procedures. `cmsis-debug-live`, `cmsis-pack-docs`, the bootstrap, board-layer and debugger-setup skills are units of the index now, not installed skills.
- **Knowledge engine (experimental).** The tools `knowledge_search`, `knowledge_get` and `knowledge_expand` over the knowledge index (`knowledge.indexPath`, `knowledge.includeIncomplete`), the **Open Knowledge Browser** panel, and the unit of a known error message in a failed build's result.
- **Knowledge that packs ship.** A pack carries its knowledge in `.knowledge/`: the units as Markdown in `units/` and `knowledge.db`, which `cmsis-knowledge build` of the Python package `cmsis-developer-assistant-tools` writes. The extension reads `.knowledge/knowledge.db` of every installed pack and offers its units only in projects that use the pack, the build's `packs:` included; parts mounted on the active board (`<mountedPart>`) count as part of the project, and the knowledge browser opens a pack unit's Markdown file from the installed pack. A `knowledge.db` elsewhere in a pack is no longer read.
- **Boards, devices and examples from CMSIS Solution's catalog: `cmsis_query`.** The first slice of #41's tool. `cmsis_query {what:'boards' | 'devices' | 'examples'}` reads the public API (version 2) of the CMSIS Solution extension, which merges Arm's web catalog with the installed packs, so the examples of a board are listed before any of its packs is installed. `vendor` and `name` (for boards also `device`) are case-insensitive regular expressions; `examples` takes the `board` or `device` id the other two list. Each answer is a short text and the same as `structuredContent`: up to `limit` entries (20) with the count of the rest, the source of each example (web or installed pack), and a note when the web catalog could not be reached. It needs no project and no session, activates the CMSIS Solution extension when it is installed but inactive, and runs in any window when several are open.
- **`cmsis_action create_solution`** creates a project from an example, reference application or template of that catalog (`board` or `device`, `draft`, `path`; `git` off by default) through the API's `createNewSolution`. CMSIS Solution then writes `.vscode/cmsis.json`, adds a `vcpkg-configuration.json` when the example brings none, and opens the folder in the window that created it, without asking. So the call runs in the window that has that folder open, or, for an agent outside VS Code, in a window without a folder, which reloads; a window with another folder, and an empty window for a chat inside it, are refused with the step that opens the folder first. The minimal project without an example stays the project procedure's.
- **`cmsis_action install_pack` installs a verified pack before the project exists.** `{action:'install_pack', pack:'Vendor::Name@version'}` runs the CMSIS Solution extension's `installPack` command (1.72.0 or later; without it the call says so), so that a pack's knowledge can be read before the project is written and no agent runs `cpackget add` in a shell. Like `open_solution` it needs no folder or solution; the router sends it to the session's window and a tie to its own window. The version is required: a pack id without one is refused, never installed as the latest. When the pack's PDSC in the pack root's `.Web/` declares a licence, the user is asked in a modal dialog (Install / Cancel) first; Cancel, or no answer within the call's wait, is a refusal that says so, and a repeated call waits for the open question instead of asking twice. Without that PDSC the pack is installed and the result says that its licence was not checked. A pack whose folder is there already is not installed again. After the command the folder is checked, and the result names the knowledge units the pack ships as a `knowledge_expand {id: "pack:Vendor::Name", relation: "scoped_to"}` call; a failure names the pack and the "CMSIS Solution" output channel, and is recorded for `get_recent_problems`. An install that outlasts the wait answers `running`, and the same call again waits for it. The `cmsis_action` schema gains the action and its `pack` argument (surface snapshot updated); the guide's bootstrap topic, the user guide and the architecture pages follow.
- **`cmsis_action rebuild`, `clean` and `stop_build`** over the CMSIS Solution commands of the same names (1.72.0). `rebuild` reads like `build`: a job (`rb-3`), the wait, ✅ or ❌, the error lines of a failed rebuild, and the check of exit 0. `clean` is a job too (`c-4`); since CMSIS Solution reports exit 0 for a failed clean as well, its result names the images of the active target it removed, or ⚠️ for one still there, and says that it covers the whole solution. `stop_build` ends a build, rebuild or clean that hangs — the CMSIS Solution command ends one build-type task, the tool terminates what is left after 3 s — and says what it stopped, or that no build was running, in which case it issues nothing. A repeated call attaches to the job in flight as `build` does; a build, rebuild or clean while another of the three runs is refused, since CMSIS Solution would start it only after that one. The `cmsis_action` enum and description change (surface snapshot updated); the guide's build topic, the user guide and the architecture page describe the actions.
- **Kimi Code in *Configure Agent* (#103).** Kimi Code, the CLI and its VS Code extension, can be set up like the other agents. Step 1 writes `{ "url": "http://localhost:3001/mcp", "toolTimeoutMs": 630000 }` into `$KIMI_CODE_HOME/mcp.json` (default `~/.kimi-code/mcp.json`): Kimi Code ends every tool call after 60 s unless the entry says otherwise, and in a September session nine `cmsis_action` and run-control calls failed at exactly 60 s. An entry under our key without `toolTimeoutMs`, as one written by hand, gets it at activation and keeps its other fields; an entry on `transport: "sse"` is replaced. Step 2 offers `$KIMI_CODE_HOME/AGENTS.md`, preselected, and the workspace `AGENTS.md`: Kimi Code does not pass the server instructions to its model, so the rule file is how the tool rules reach it. Sessions of the client `kimi-code` get tool results without `structuredContent`, which Kimi Code appended to the text as JSON (17 KB of 95 KB in that session), and their first `get_session_status` carries the whole tool rules instead of the line that points at the server instructions, which a Kimi Code 2.3.2 session confirmed its model never sees. Their `GET /mcp` gets 405, so Kimi Code opens no SSE stream: when the stream dropped at a restart of the endpoint (a router window reloaded or closed), its client gave up after two retries within 2.5 s ("Maximum reconnection attempts (2) exceeded"), Kimi marked the server failed, and every Kimi session opened or resumed afterwards had no CDA tools until the window reloaded; now the first call after a restart gets 404 and Kimi reconnects. `cmsis-help` gains `when_to_use` (Kimi Code lists only the first 250 characters of a description) and a section on what to do when the tools are missing: start a new agent session once VS Code serves, no sub-agent, no pyOCD or GDB in a shell. A request on any path other than `/mcp` and `/sse` gets a JSON-RPC error that names the endpoint instead of Express's HTML "Cannot POST /", which a hand-written entry without `/mcp` produced. The user guide has a manual entry for Kimi Code, its rule file and a troubleshooting note on its start order and approvals.

### Changed
- **The tool rules say what they cover, and hold only the scope and the bans (tester feedback).** Users could no longer run `gdb` for a project or a target the extension does not serve: the rules sit in user-level rule files (`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, …) and in the server instructions of every session, and their first line, "Only the user can lift a rule", told the agent not to judge whether the rules applied at all. The block now opens with its scope: Arm Cortex-M targets of the CMSIS Debugger (`gdbtarget` launch configurations, CMSIS solutions); a host program or a board of another toolchain is not covered, and the agent's usual tools apply there; for a covered target only the user lifts a rule. The rules are six bullets and 1 435 bytes instead of nine and 1 596: the three lines that are not bans moved to where they apply. "A running target rejects reads and steps: call `pause_execution` first" is in the sentence on reading results, next to `TARGET_RUNNING`, whose reply carries the same hint; the control server and the registry files, and `list_debug_windows` with `select_debug_window`, are a sentence of the server instructions; and the setting that enables a missing tool group is named by the instructions of a session that has it off, which now holds for the build-artefact tools as well as the documentation tools. The build rule names a procedure from `knowledge_get` next to a CMSIS skill as what may call `cbuild`, `csolution` or `cpackget`, so the instructions no longer have to say that a knowledge procedure counts as a skill. The server instructions, the skills, `debug_instructions.md` and `cmsis-help` carry the new text (surface snapshot updated); the user guide and the server page say what the block holds and why. A rules block the setup wrote into an agent's rule file is offered the update at the next activation, and **Configure Agent** offers it again at any time.
- **Only `cmsis-help` remains in the extension.** The eight procedure sources, their assets and catalog metadata, and the routing definitions now belong to `cmsis-knowledge-base/sources/cda-procedures/`. Their procedure and asset IDs stay unchanged in the pinned `core-2026.10.29` index. The knowledge base also fetches Open-CMSIS-Pack/cmsis-skills directly; the extension no longer vendors those skills or generates a router. `npm run skills:sync` writes the one-entry installer catalog and the tool-contract blocks, and checks every `$name` hand-over against the pinned index. Content validation lives with the sources; extension tests check the procedures in the shipped index. Legacy managed skills are still removed on upgrade, while personal skills are preserved.
- **The version the server reports is read from `package.json` at build time.** It was a literal in `src/debuggingExecutor.ts` that a release had to keep in step by hand; a CI build of a tag now reports the tag's version.
- **The tool rules say what they are about.** They sit in user-level files that agents read in every project, so the lines that read as bans in general now name their subject: `pyocd`, `gdb`, `JLinkExe`, `JLinkGDBServer` and `openocd` are not run *against the board* from a shell, and the build-artefact tools answer *firmware* symbol, section, memory-usage and build-log questions. A `gdb` on a host program, or `nm` on a host binary, is no longer forbidden in passing. Two lines are shorter to keep the rules under 1 600 bytes. The server instructions, the skills, `debug_instructions.md` and `cmsis-help` carry the new text (surface snapshot updated).
- **A release no longer rewrites your rule files unasked.** When the rules change, activation offers once, in a toast, to review the update of the blocks it wrote earlier; **Review** shows each file as a diff with the modal **Write** of the setup step, **Not Now** leaves the files alone and **Configure Agent** offers the update again. Until now activation rewrote the blocks in place and only logged it. The toast is not repeated for the same rules, waits while the first-run setup is due (its rules step offers the update itself), and activation does not wait for the answer. *Reset Popup State* makes the offer due again.
- **The documentation, knowledge and flash tools ask the CMSIS Solution extension which target is active.** Without a `target`, `cbuildRunFile` or `pack` argument they take the cbuild-run file of its active target (`getCbuildRunFile`) instead of choosing among the workspace's `*.cbuild-run.yml` files, and they look for the target's packs first in the DFP and BSP folders it names (`getDfpPath`, `getBspPath`), each counted only when its PDSC is the pack being looked for. The extension is asked only while it is active, each command only when the installed CMSIS Solution version has it, for at most 3 s; otherwise the workspace scan, `launch.json` and the pack root decide as before. The answers of the extension's getters are read in one place, `src/core/solutionAnswers.ts`.
- **A `tasks.json` without CMSIS tasks is written for you when the target names a debugger.** `load`, `erase`, `run` and `load_and_run` refused at once when the solution's `.vscode/tasks.json` had no CMSIS task. When the active target's cbuild-run.yml names a debugger, the tool now runs CMSIS Solution's *Update Debug Tasks and Launch Configurations* (`cmsis-csolution.updateDebugTasks`, what that extension runs after each successful convert) once, reads the tasks again and goes on; the result says so. It does not when no debugger is named, when no cbuild-run.yml exists yet, or when `cmsis-csolution.autoDebugLaunch` is off; then, and when the command wrote nothing, the refusal says which and names **Manage Solution Settings** (`cmsis-csolution.manageSolution`) and its Debugger page.
- **The status-bar item is the CDA robot.** Every window shows the robot icon with **R** (router) or **W** (worker) instead of the plug with "CDA router"/"CDA worker"; the tooltip's default-target line reads "Default target windows:" and the hints that name the status bar say "the CDA robot icon" (#87, the icon only; the wording "sessions" and the command title stay open). The icon is the product icon `cda-robot` of `package.json`, a one-glyph WOFF font under `assets/icons/`.
- **The core knowledge index is pinned, not copied in by hand.** `resources/knowledge/core.lock.json` names the index by version and sha256 (a release `core-<version>` that the knowledge base builds reproducibly from a commit and publishes in the public repository [cmsis-knowledge-index](https://github.com/MatthiasHertelArm/cmsis-knowledge-index)); `npm run knowledge:fetch` downloads it from the knowledge base's releases, hash checked, `npm run knowledge:check` verifies, `npm run knowledge:update -- <version>` moves the pin. Packaging refuses a VSIX without the pinned index, so CI can no longer package the knowledge tools without their index as the first 2.7.0 pre-release builds did.
- **The sources of the knowledge index are attributed.** `resources/knowledge/SOURCES.md`, generated by the knowledge base and shipped in the VSIX, lists every source of the core index with repository and licence and what was taken (Agent Skills, tool messages, documentation, issue digests in own words), carries the copyright lines and licence texts of the MIT and BSD-3-Clause sources and the NOTICE files of the Apache-2.0 ones, and names the repositories whose issues are summarised. The lock names the release's copy (`sources`, `sourcesSha256`); `knowledge:fetch` refreshes it, `knowledge:check` and packaging hold it to the hash. NOTICE gains a "Knowledge index" section and `TPIP.md` the table of sources.

### Fixed
- **`read_memory` evaluates nothing that writes, and a word of hex letters is a name (Windows test of 26 Oct, K05).** Since an address may be an expression, GDB evaluated whatever came: `read_memory {address: "ptr = 0"}` set `ptr` before the read, and `mutate()` called the function on the target. An expression with an assignment (`=`, `+=`, …), `++` or `--`, a function call or a string literal, which GDB copies into target memory, is now refused with `INVALID_ARGUMENT` before GDB sees it. `face`, `dead` and other words of hex letters were read as the addresses 0xface and 0xdead although they are valid symbol names; they are now evaluated as names, and when no such symbol exists the hint says to write `0xface` for the address. Hex digits that start with a decimal one, `20000000`, stay an address.
- **Variable listings read a scope of program variables that the adapter marks expensive (Windows test of 26 Oct, K03).** On the CMSIS Debugger, a read of all scopes left out every scope marked expensive, to skip the Registers scope; a scope of statics or globals so marked was skipped too. Only a register scope (by its `presentationHint` or its name) is left out now.
- **A symptom pattern can no longer stall the extension host (Windows test of 26 Oct, K01).** The guard refused an unbounded quantifier inside an unbounded group but let `(a|aa)+$` through, which backtracks for seconds on a line of 40 `a`s; a pack's knowledge index could freeze the router window with it. Symptom patterns are now compiled into a matcher that never backtracks, with limits on a pattern's length and states and on the work of one search; quantified groups, back-references and lookarounds are refused and counted as unusable. All 685 symptom patterns of the core index compile and match as before.
- **`cmsis_action` with `target` reads target-types in every form YAML allows (Windows test of 26 Oct, K02).** The target-types were read line by line; a target-type written as a flow mapping (`- { type: MPS3 }`), an alias, a merge key or a tag was missed without a word, so the switch said the target was not declared, or could point a set's index at another set. They are now read with a YAML parser (js-yaml). A csolution that is not valid YAML, or whose target-types have another shape, ends the switch with `INVALID_ARGUMENT` before anything is written.
- **The YAML the CMSIS tools write is read by a YAML parser (#102).** The build diagnosis read `cbuild-idx.yml` and `.cmsis/tools-environment.yml` with a reader for a subset of YAML, which misread a comment after a key, a flow sequence such as `[elf, hex, map]`, a comment inside a list item, and the blank lines and final newline of a literal block. It now uses js-yaml, which the target-types already used, with every scalar kept as a string and an empty value as null; a file that is not YAML yields no messages instead of misread ones. Over 4 930 CMSIS YAML files on one machine, the 225 `cbuild-idx.yml` and 65 `tools-environment.yml` files read exactly as before; the differences in csolution, cproject, clayer and cbuild-run files are all the old reader's misreadings.
- **Two windows no longer start GDB servers on the same port at the same moment (Windows test of 26 Oct, K04).** Each window checked on its own that a launch configuration's fixed GDB port was free; two starts at the same moment both passed the check, and the second server failed with EADDRINUSE. A start now reserves its port across the windows before the check and holds it until its session or task ends; the other start is refused with `PROBE_BUSY`, which can name a start whose server is not open yet.
- **A GDB port reservation covers the active target's launch only, knows the pyOCD of a custom debug setup, and ends with its session (tester feedback on preview 4).** On an STM32H7 with a custom debug setup (an adapter template of its own), `load_and_debug` failed with `PROBE_BUSY` for port 3334, the port of an FVP configuration that `launch.json` kept beside the board's (`updateConfiguration: manual`): every launch configuration was reserved and asked about, though CMSIS Solution starts only the one of the active target's debugger. It now takes the configurations of that debugger's kind (FVP or not) on the GDB ports of the active cbuild-run.yml, and all of them only when neither fact narrows the list. The board's own port 45343 was never reserved or published: its adapter template starts pyOCD's `gdbserver` through Python and a wrapper script and renders the port in quotes (`"\"45343\""`), and both went unrecognised. A `gdbserver` that passes `--cbuild-run` now counts as pyOCD whatever starts it, and a quoted port is read, and a pyOCD launch or session without a fixed port takes the port from the cbuild-run file it passes to `--cbuild-run` (the one port of the active target's file for a launch, the resolved file for a live session); a fixed port comes first. A reservation was also released only once a port sample had seen its session live: after a reply that came early (a short `timeoutMs`), a session whose launch failed — VS Code never announces such a session — or that ended before the next sample kept the port reserved until its window closed, and the next start on that port, in that window too, got `PROBE_BUSY`. A session now takes the reservation of its ports when its adapter starts, and its end releases it.
- **A stop cut short by the call's deadline is reported as pending (Mac test of 27 Oct).** `stop_run` and `stop_build` with a short `timeoutMs` failed with `TASK_FAILED` while the task was still ending, and then showed as stopped. The reply now says the stop was requested and is pending, names what still runs, and points to `cmsis_action {action:'status'}`; the task is not terminated a second time early.
- **Windows and macOS: the CMSIS tasks of a folder are found when its path differs in case (Windows CI).** The label pre-check of `cmsis_action` took a task as the solution folder's only when both paths were equal character for character; VS Code writes a Windows drive letter in lower case (`c:\…`), a path from elsewhere may not, and the CMSIS tasks then counted as missing: Update Debug Tasks ran, or `load`, `run` and `attach` were refused. The paths are compared as file names compare on the platform. The result of `activate_environment` names `.cmsis/tools-environment.yml` with a forward slash on Windows too.
- **Windows: a write that a virus scanner blocks for a moment is tried again (Windows test of 26 Oct).** The atomic writers rename a temp file onto the target; on Windows that rename fails for a moment while a virus scanner holds the file just written, and a window registry entry could keep its last state, "debugging" after the session had ended; three window-coordinator tests found such a stale flag on the Windows test machine, and this is the likely cause. The rename is now tried again on EPERM, EACCES and EBUSY, for up to 310 ms in the synchronous writer and 1.3 s in the asynchronous one. The build-information tests copy their fixtures with fresh modification times, since Windows' CopyFile keeps the source's and the comparison of a log with its image failed there alone.
- **Kimi Code in VS Code gets the CMSIS tools after a start or a reload (Kimi Code tester session).** Kimi's VS Code extension connects to its MCP servers once, at its own activation, and never retries; the endpoint came up 0.7–1.7 s after this extension started to activate, because the skill was installed first, and Kimi lost 6 of 7 starts that day. Activation now binds the endpoint before it installs the skill, migrates agent files or offers rule updates, and a workspace with a `*.csolution.yml` activates the extension during start-up instead of after it.
- **A second entry for this server in an agent's file is removed (Kimi Code tester session).** *Configure Agent* wrote `cmsis-developer-assistant` next to a hand-written "CMSIS Developer Assistant" entry; Kimi Code listed every tool twice, its model called the copy without `toolTimeoutMs`, and calls ended at 60 s. Configure Agent and activation now remove any other entry that reaches this server (a loopback URL on its port at `/mcp` or `/sse`) next to ours, merge its `autoApprove` list, and say which keys went. A cut wait's note in a Kimi Code session names `toolTimeoutMs` as the setting to raise.
- **A Load that waits for a probe is called stuck after 2 minutes (Kimi Code tester session, case 2510-MH).** A CMSIS Load that waited for a probe without a Windows driver ran 30 minutes while 15 `status` replies said "This is not a failure … do not start it again", each after a 48 s wait. A Load or Erase task alive for 2 minutes is now reported as stuck, with the probe causes and `stop_run`, which ends it; `status` answers such a job at once, and `get_session_status` and `status` without a job say the same of a task started from the UI.
- **`fetch_doc` downloads finish (Kimi Code tester session).** The download ran on the call's deadline and was deleted when it passed, so 24 calls in a row started over and none finished, while the reply said the work went on. A download is now a job of its own of up to 10 minutes: a call that waits too short answers `running` with the bytes so far, later calls join the same download and index the PDF once it is in, and from the second failed attempt the reply asks the user to put the PDF into the workspace docs folder.
- **Breakpoints in pack sources reach the session (Kimi Code tester session).** `add_breakpoint` on an ExecuTorch or SDS source in the pack root was refused with "No open VS Code window has … inside its workspace", with one window and a live session. A file that no window's folders contain now goes to the window the session's other calls go to, and the answer says so; with no such window it is refused as a tie that names the file.
- **Agent and contributor guidance matches the 2.7.0 tools.** Corrected GDB passthrough, active-session attach, conditional launch/task repair, timeout limits and the FVP recovery exception; documented knowledge controls and catalog/download traffic. Skill fallback depends on client capabilities. The agent resource text and server instructions have matching surface snapshots. Packaging and clean-checkout instructions include the pinned knowledge index; obsolete plans are labelled historical and broken evidence links point to the reviewed commits.
- **Documentation checks run before merge with the pinned index available.** CI includes Markdown-only changes and fetches the index before the contract tests. TPIP regeneration watches its knowledge inputs; the feature-request form is valid YAML and the unused former link-check configuration is removed.
- **The evaluation launch verifier checks only its own Docker containers.** Native model verification no longer requires Docker; the macOS fixture check filters by workspace and does not fail because an unrelated container is running. Setup guidance uses the correct helper path after building and states the separate native-model prerequisite.
- **`read_memory` reads at an address expression such as `&buffer` (Kimi Code session).** The guide sends agents to "`read_memory` at `&adc_buffer`", but the tool put `0x` in front of whatever it got: Kimi Code's `read_memory {address: "&bulkOutBuffer"}` came back as `[INTERNAL] Cannot convert 0x&bulkOutBuffer to a BigInt`, after the adapter's `Invalid number "0x"`. An address that is not hex digits is now evaluated by GDB as `(unsigned long)(expression)` in the focused frame — `&buffer`, an array name, a pointer, `&s.field` — and the dump header names both (`Memory at 0x20000100 = &bulkOutBuffer (64 bytes):`). An expression GDB cannot place is refused with `INVALID_ARGUMENT`, GDB's message and how to pass an address. The `address` description in the schema says so (surface snapshot updated).
- **The knowledge index carries this release's procedures and three corrected symptom patterns (tester feedback).** The pinned core index moves to `core-2026.10.29` (7 145 units, knowledge base commit `bff5475`), built from the knowledge base's procedure sources: `proc-debugger-troubleshooting` gains its first check, "The probe's software is missing or not on PATH", and finds the J-Link error lines in a search; `proc-cmsis-debug-live` and `proc-fvp-debug-setup` have the attach-reconnect wording, the Arm FVP pause facts and the topics `target`, `cmsis-action` and `flash` in place of `build`. Two csolution messages that print one of two texts (`no default unnamed target set for …` / `target set … not found`, and `'device: Dname'` / `'board:' node … is deprecated at this level`) match their units with either text; `'JLink.exe' is not recognized as an internal or external command` no longer names an issue digest about a µVision path, whose pattern matched any program cmd.exe could not find. The golden set is unchanged. Two documentation sources that are not public are left out with their nine units, and the index is published in a public repository of its own, since the knowledge base's is private.

- **`open_solution` activates the solution in the window that has it open, however the path is written (#84).** The CMSIS Solution extension takes a csolution only as an exact entry of its own list, and otherwise waits in its "Select a solution" picker. A path that differed from VS Code's spelling of the open folder (on macOS in letter case, on any system through a link) opened a second window instead of activating the solution there. Inside the folder, the path was matched against a search with other exclusions and at most 200 results. So a csolution in `build/`, `out/` or `tmp/`, or beyond the first 200, still reached the picker unless it was written exactly as listed, and one in a hidden folder, which the extension never lists, always did. `open_solution` now runs the extension's own search (every csolution file, with hidden folders and `cmsis-csolution.exclude` left out) and compares paths by their real path. It refuses a csolution the extension does not list with `INVALID_ARGUMENT` before the extension is asked. A solution already active under another spelling is no longer refused under a live debug session.
- **`cmsis_action attach` no longer connects to the GDB server before it attaches.** To refuse an attach without a server at once, it opened and closed a TCP connection on each attach port of `.vscode/launch.json`. A GDB server takes that connection as a client. pyOCD halts the target when a client connects and resumes it when the client leaves, so firmware started with `cmsis_action run` (`--reset-run`) stopped briefly before the real attach. A pyOCD server without `--persist` shut down on that connection, so the attach then failed with "could not connect"; this hit the server the user restarts by hand to reconnect without a reset, as the `PROBE_WEDGED` hint asks. The check now goes by what the window knows and connects nowhere. While its CMSIS Run task is an FVP model without the GDB server plugin (seen in the task's command line, or from the target's `Arm-FVP` debugger for a model shim), `attach` is refused with `NO_SESSION` and `load_and_debug` as the way, as before. Without a CMSIS Run task it is no longer refused at once, since a server started outside the window may be listening. GDB's own connect decides, and a reply that is still `running` says that without a server the session ends at GDB's 15 s connect timeout and that, with a probe adapter, `cmsis_action run` starts one.
- **`flash` programs the probe that CMSIS Load programs, and a load that exits 0 is a success.** `flash` ran `pyocd load` without the `--probe` and `--uid` of CMSIS Solution's CMSIS Load task, and pyOCD selects no probe from the cbuild-run file: with two probes connected it stopped at pyOCD's own prompt ("EOF when reading a line"), and with only another board's probe connected it programmed that board, whatever probe ID was set. It now passes the probe type of the target's debug adapter (`cmsisdap:`, `stlink:`, `jlink:`) and the probe ID from the cbuild-run file's `debugger:` or the setting `cmsis-csolution.probe-id`; several probes and none selected is `TASK_FAILED` listing their unique IDs and where to set one. A flash also failed whenever an output line contained "error", "failed" or "exception", such as pyOCD's `Loading <path>` line for a path with `ErrorHandling` in it, or a warning, and answered "Flash FAILED (exit 0)". pyOCD's exit status now decides: a failure shows its error and critical log lines, tracebacks and probe messages, and a success lists what pyOCD warned of. When pyOCD could not add part of the image ("Failed to add data chunk", which it skips before exiting 0), the answer is ⚠️ and says to check the section addresses with `get_section_layout` or `lookup_symbol`.
- **The SVD tools find the SVD of a local device pack, of a session VS Code has not focused, and on Windows.** A `*.cbuild-run.yml` names the SVD of a pack outside the pack root (`packs: - path: ../DFP`) relative to its own folder (`out/`), but the entry was resolved against the extension host's working directory, so `read_peripheral_register`, `lookup_peripheral`, `lookup_register` and `diagnose_fault` found no SVD; it is now resolved against the cbuild-run file's folder, as pyOCD and the CMSIS Debugger do. The SVD entries were also read with an LF-only line split, so a cbuild-run file with CRLF line endings, as csolution writes it on Windows, gave no SVD at all; CRLF is now read too. The tools also took the SVD of VS Code's focused session while the reads went to the session they act on (the focused one, else the most recently started): with focus elsewhere, as multi-core launches often leave it, `read_peripheral_register` answered "No SVD file found", and the lookups and `diagnose_fault` fell back to the workspace and the first core's SVD. They now take the SVD of that session, including its launch `svdFile` unless the call names another core with `pname`; the lookups used to skip it.
- **`read_peripheral_register` reads through the device SVD without probing the Peripheral Inspector, and its description says so.** Before each read, the reader looked up the `eclipse-cdt.peripheral-inspector` extension and activated it if it was not active yet. It then probed the extension's API for register reads that the API does not have (in 1.10.0 it registers SVD files and parsers, returns interrupt tables and reloads its view), so every read fell through to the SVD path anyway. The probe is gone; reads and replies are unchanged. The tool description said the SVD data came from the Peripheral Inspector and that without it the tool points to `read_memory`. In fact that guidance comes when no SVD file is found, and the description now says so.
- **`reset` with `method: 'hardware'` pulls the reset pin on J-Link.** For the `hardware` method the J-Link GDB server got `monitor reset 0`, the same command as for `system`. Strategy 0 is J-Link's normal reset, SYSRESETREQ on most devices, so nSRST was never pulled, and the last step of `auto` repeated the system reset; a part that only a pin reset brings back stayed unreset. `hardware` now sends `monitor reset 2`, J-Link's reset-pin strategy, as the CMSIS Solution J-Link launch templates do for the csolution reset type `hardware`; `system` (0) and `core` (1) are unchanged. The reset commands that would leave the target running, which the tool does not use, are corrected too: pyOCD read no reset type from `monitor reset run system`, so that form is now `monitor reset system`, and J-Link's form ends with `monitor go`.
- **`read_cycle_counter` finds the cycle counter on every core that has one, and says so when a core has none.** It read `DWT_CTRL.NOCYCCNT` at bit 28, the lowest bit of `NUMCOMP`, instead of bit 25. A core with a cycle counter and 1, 3, 5 or 7 DWT comparators was reported as having none. A Cortex-M23, or a Cortex-M0/M0+ with an even number of comparators, failed with "Write to 0xE0001000 did not stick". `NOCYCCNT` is now read at bit 25. Armv6-M and Armv8-M Baseline cores (Cortex-M0, M0+, M1, M23) never have a cycle counter, and Armv6-M has no `NOCYCCNT` bit at all. These cores are now recognised by `CPUID` before anything is written to the target.
- **`read_memory` shows each byte at its own address when the start of the range cannot be read.** cdt-gdb-adapter answers a range that begins in a hole of the memory map with GDB's first readable block, at that block's address. The dump printed those bytes from the requested address on: 64 bytes read at 0x1FFFFFF0 showed the SRAM contents of 0x20000000 under 0x1FFFFFF0. The executor now places a reply's bytes where its address says, and the dump labels its rows from there. A partial read, at the start or the end, adds a line with how many bytes were read and which addresses could not be. `diagnose_fault` and `get_fault_info` use the stacked frame and the fault-register block only when they begin at the address asked for.
- **Variable listings on the CMSIS Debugger no longer read every register over the probe.** With their default scope `all`, `get_variables_values`, `list_variable_names` and `get_frame_variables` also read cdt-gdb-adapter's Registers scope, which the adapter marks expensive. On a Cortex-M4F or M7, every call fetched all core and FPU registers (s0–s31, d0–d15, …) through the probe and listed them next to the locals. On the CMSIS Debugger, `all` now leaves out the scopes the adapter marks expensive, which VS Code also reads only once they are opened, and one line names them and points to `read_core_registers`. `local` and `global` still read whatever scope matches, and other debug adapters keep every scope.
- **A CMSIS Debugger session that is still connecting, or shutting down, is `initializing`, not `running`.** cdt-gdb-adapter answers every request with an empty success until GDB has connected to the target and run the launch configuration's commands, and again while the session ends, and the session probe took that for a live session. During `cmsis_action load_and_debug` and `attach`, `get_session_status` said `running`, reads were refused with `TARGET_RUNNING` and "call pause_execution first", `pause_execution` sent a pause the adapter skipped and waited for a stop until its timeout, and `cmsis_action` stopped waiting for the session at its first look. On `gdbtarget` sessions a `threads` reply without a thread list now counts as `initializing`: the gates refuse with `NO_SESSION` and "wait and retry", `check_target_connection` reports `NOT READY`, `cmsis_action` waits until the adapter takes requests, and a session that ends before it comes up is `TASK_FAILED` at once. Other adapters keep their answers.
- **`diagnose_fault` reads the exception frame of a TrustZone fault from the stack that holds it.** On Armv8-M with the Security Extension it decoded only bits 2 and 4 of `EXC_RETURN`. A frame on the other Security state's stack was read from the handler state's MSP or PSP: a SecureFault or Secure HardFault taken from Non-secure code, or a Non-secure handler entered from Secure code. A frame with the additional state context was read 40 bytes too low, so its "stacked PC" was R8. It now follows `EXC_RETURN` S, ES and DCRS as the architecture unstacks them. It reads the other state's banked `msp_s`, `psp_s` and `control_s` (or the `_ns` ones) only for such a frame, finds R0 at +0x28 behind the integrity signature and R4–R11, and checks the signature. When the GDB server does not report the banked registers, the reply says so instead of reading the wrong stack. Armv6-M and Armv7-M frames read as before, and the embedded guide's offset of the stacked PC in an FP-extended frame is corrected from SP+104 to SP+24.
- **Two `serial_open` calls at once no longer leave a second port open.** The window's port was checked before the open finished, so two MCP sessions opening ports in the same window both got one. The first stayed open, fed its bytes into the other's buffer, and was closed neither by `serial_close`, the idle release nor the end of its session; its idle timer later released the second port. Two opens of the same device answered the second with "another program holds it". Opens and closes in a window now take turns: a `serial_open` or `serial_capture` that arrives while another open is in flight waits for it and is then `PORT_HELD` as it would be afterwards (or opens, when the first one failed). A `serial_close` arriving meanwhile closes that port, an open right after a close or a release waits until the device is let go, and the end of an MCP session releases a port that session was still opening.
- **The Serial Monitor bridge reaches the Serial Monitor's API, and no hint sends agents to read the user's Serial Monitor session any more.** The bridge took the exports of `ms-vscode.vscode-serial-monitor` for its API. They hold only `getApi(version, context)`, so `serial_status` listed `getApi` as the API and `serial_subscribe_monitor` blamed the installed build. The bridge now asks `getApi` for version 0 with the extension's context, as the CMSIS Solution extension does. `serial_status` lists the API's methods. `serial_subscribe_monitor` says that this API has no data event and what to do instead: ask the user to stop monitoring the port, then use `serial_capture` or `serial_open`. The `PORT_HELD` hint, the shell-to-tool table of the tool rules, the guide and the `cmsis-debug-live` skill now say the same instead of naming `serial_subscribe_monitor`. The descriptions of `serial_subscribe_monitor` and `serial_open_monitor` no longer promise the Serial Monitor's data. `serial_list_ports` keeps listing with the bundled serialport, because the Serial Monitor's list is the same without the serial numbers, and it now shows the friendly name Windows gives a port (surface snapshot updated).

### Fixed
- **`cmsis_action build` no longer reports ✅ for a build that failed to compile (part of #15).**
  - CMSIS Solution 1.70.1 closes its build task with exit code 0 whatever cbuild returned: its build runner drops the exit code, and the task's pseudoterminal then closes with 0. A tester got "✅ CMSIS 'build' succeeded … exited 0 after 3 s" four times while cbuild failed with `call to undeclared function '__disable_irq'`, and the image stayed 37 minutes old. The job tracker bound the right execution; the 0 came from CMSIS Solution.
  - A build whose task exits 0 is now checked before it answers. Errors in a fresh `cbuild-idx.yml` fail it. Images all written since the build started confirm it. Otherwise the diagnostic re-run of #15 decides: a build that fails there answers `TASK_FAILED` with its error lines ("exited 0 after 3 s, but the build failed"), and one that succeeds is reported as up to date.
  - When an image was not rewritten and the re-run cannot run (setting off, no `.cmsis/tools-environment.yml`, another build running), the result is a ⚠️ warning that exit 0 does not confirm the build, with the reason, instead of ✅. `status` and `get_session_status` show `❌ build errors (exit 0)` or `⚠️ exit 0, not confirmed`; `data.diagnosis.check` carries `rebuilt`, `up-to-date`, `failed` or `unverified`.

- **Every `structuredContent` carries the text of its result, so a client that shows the model that object instead of the text loses nothing (part of #11, #48).**
  - Some MCP clients hand the model `structuredContent` and not `content`. An ok reply with data carried only `{status: 'ok', ...data}`, so `get_recent_problems` reached such an agent as `{"status":"ok","nextSeq":27,"returned":2,"omitted":0}`, without a single record.
  - An ok reply with data now carries its text as `message`, as the timeout, running and error shapes already did.
  - `get_recent_problems` also returns its records as JSON in `structuredContent.records`, the same records as its lines. The lines and the records each stay within 8 kB; what does not fit counts as omitted.
  - The surface and DAP oracles fail any reply whose `structuredContent` leaves out a line of its text.
- **`continue_execution` no longer halts the target when its wait runs out.**
  - A continue that saw no stop within its wait went down the steps' recovery path, which paused the target to report where it was. An agent that continued to let the firmware run, with a short `timeoutMs`, found it halted afterwards.
  - It now answers with status `running` and leaves the target running: "Target is running: no stop within 500 ms of 'continue_execution', and it keeps running; nothing was paused. Call wait_for_stop …, or pause_execution …".
  - The steps keep their recovery pause and its report of PC, LR and source line.

### Security
- **The window registry and the control servers are closed to other local users (#19).**
  - Every VS Code window publishes its control port and token in the registry, and the token is enough to flash or erase that window's board. The directory was created 0755 and the files 0644, so on Linux, where it sits in the shared `/tmp`, any local user could read every token.
  - The directory is now 0700 and each window file 0600. An existing 0755 directory of the user is narrowed on first start, and each window rewrites its file 0600 within 20 s.
  - Where every user may write to the temp directory (Linux `/tmp`, macOS with `TMPDIR` unset), the directory name carries the uid: `cmsis-developer-assistant-registry-<uid>`. The per-user temp directories of macOS and Windows keep the old name.
  - A registry directory that is a symbolic link or belongs to another user is neither written nor read. The window logs an error, shows one warning, and keeps serving its own tool calls; only the other windows are out of reach.
  - The control server refuses a request whose `Host` is not loopback or that carries an `Origin` at all, before it looks at the token, and compares the token in constant time. Its 403 and 404 answers, and a new `_note` field first in each registry file, tell an agent that found them to use `list_debug_windows` and `select_debug_window`.
  - The registry format and the protocol between windows stay compatible with 2.5.0 and 2.3.10.
  - **Linux: reload every VS Code window after updating.** A window that was not reloaded keeps using the old registry directory and is invisible to updated windows until it is reloaded. On macOS and Windows the directory name does not change.
- **Agent configuration files keep their permissions when the setup rewrites them.** The atomic writers created a new file with the default mode, so a `~/.claude.json` or other agent configuration that its owner had narrowed to 0600 came back readable by every local user after the server was registered in it. A replaced file now keeps its permission bits.

  - Binding is now reported from the adapter's `verified` state and message, and `list_breakpoints` shows it.
  - On `gdbtarget`, logpoints are GDB dprintfs (MI `-dprintf-insert`), so `{expr:%08lx}` is filled in and a condition really applies. They are tracked by number, removed and cleared by number (never a bare `delete`), and listed with their hit counts. Other adapters keep VS Code logpoints.
- **Breakpoint changes and restarts are safe while a CMSIS target runs (#13).**

- **`get_debug_instructions` takes a `topic`** — the guide for harnesses that do not load skills (GitHub Copilot Chat) no longer arrives as one 21 KB block. ## [2.0.0] - 2026-08-10

Upstream sync: the fork was based on `microsoft/DebugMCP` `4422d8c` (2026-03-14) and had cherry-picked three commits since. Upstream is 102 commits ahead at v2.3.0. This release takes what applies to Cortex-M, adapts what does not, and says which is which.

It also carries the hardware-tool work that had accumulated unreleased on `feature/hw-tools-reset-wait-flash-dwt`.

**Major, not minor.** Three things change behaviour an existing setup can depend on:

- **A window no longer always runs its own MCP server.** One window binds `serverPort` and routes to the rest; the OS-assigned fallback port is gone. Anything that discovered a per-window port, or assumed "my window = my server", has to change. This is the fix for agents driving the wrong board, so the old behaviour is not coming back.
- **The MCP transport is stateful.** Clients must carry the `mcp-session-id` from `initialize`. Every SDK client does; a hand-rolled client that POSTed bare JSON-RPC will now get a 400.
- **`add_breakpoint` prefers `line` over `lineContent`.** `lineContent` still works and is not going away this release, but it is deprecated and the response says so.

It also matches upstream's 2.x line, which this release syncs against.

### Added — hardware tools
- **`wait_for_stop` tool** — block until the target next stops (breakpoint, fault, step-complete, pause) and return the stop reason plus the current debug state, or a structured timeout. Built on raw DAP `stopped` events from the session tracker (the ground truth), not VS Code UI events. Returns immediately with the recorded reason when the target is already stopped. This replaces sleeping blind after `continue_execution` returned while the target was still running — the pattern that once missed a 15 s playback window.
- **`reset` tool** — reset the target inside the live session (breakpoints and session survive, unlike `restart_debugging`) via GDB monitor commands, and **verify the reset actually took effect**: after the reset-halt the PC must equal the reset handler read from the vector table (VTOR-based, falling back to table base 0). `method: auto` escalates `system` → `core` → `hardware` until one verifies; adapter replies that read like "unknown command" escalate instead of being trusted. Unverified resets are reported honestly ("target does NOT appear to have reset", with the adapter replies and the nSRST wiring caveat) — silent non-resets on attach configurations were a recurring field issue.
- **`read_cycle_counter` tool** — DWT CYCCNT for cycle-accurate timing: enables `DEMCR.TRCENA` and `DWT_CTRL.CYCCNTENA` when needed, reports `NOCYCCNT` cores honestly, and prints the wrap (~10.7 s @ 400 MHz), core-halt, and WFE-sleep caveats with the two-point delta recipe.
- **`flash` tool** — `pyocd load --cbuild-run <file>` as a synchronous operation: bytes programmed + rate on success, exit code + pyOCD error/output tail on failure. The cbuild-run file is auto-resolved from launch.json's `cmsis.cbuildRunFile` or a recursive `out/` scan; ambiguity is an error naming the candidates, never a silent pick. Refuses while a debug session is active (programming under a live session wedges most probes). Requires pyocd on PATH; `cmsis_action load` remains the bundled-pipeline alternative.
- **Launch-failure diagnostics passthrough.** The session tracker now keeps a bounded per-session ring of recent adapter traffic (failed DAP responses, adapter stderr/console output — `stdout` excluded so target printf can't flush real errors out). `start_debugging` failures and the `cmsis_action load_and_debug` / `attach` "did NOT survive the initial connect" report append it, instead of leaving the real cause in the extension-host log.

### Fixed — hardware tools
- **`read_peripheral_register` decoded full-word SVD fields as 0.** `decodeFields()` built its mask as `((1 << width) - 1) << bitLow`, but JS bitwise ops coerce to int32: `1 << 32` wraps to 1, so any `[31:0]` field got mask 0 and silently decoded to `0x0` for every register value; width-31 fields were corrupted by the negative `(1 << 31) - 1`, and fields touching bit 31 could print negative. The decode now shifts first (`>>>` is ToUint32) and masks with `2**width - 1` (exact for width ≤ 31), so no intermediate is ever a negative int32. Covered by new unit tests (widths 1/8/31/32, high-bit fields, negative-input normalization).
- **Parsed-SVD cache is now invalidated when a debug session ends.** `clearSvdCache()` existed but had no callers, so a session against a different device could have kept the previous device's decode.
- **Memory writes are verified.** New `writeMemoryWord` executor primitive (DAP `writeMemory` with GDB-`set` fallback) always reads the word back and throws "did not stick" on mismatch — a silently dropped write is exactly how "reset did nothing" happens in the field. Shared by `reset` and `read_cycle_counter`.

### Added — upstream sync
- **`add_logpoint` tool** — print a message and resume instead of halting, bound GDB-native via `dprintf`. Expressions interpolate as `{expr}`; GDB infers nothing about types, so `{expr}` defaults to `%d` and `{expr:%s}` / `{expr:%f}` / `{expr:%p}` override it, with `{{`/`}}` for literal braces. `dprintf` takes no inline `if`, so a `condition` is attached afterwards by breakpoint number — and the response says plainly when the adapter echoed no number to attach it to, rather than pretending the condition applied. The tool description does not claim logpoints are free here: the core still halts on every hit to format and print, which in an ISR or a hot loop distorts the timing you are usually measuring.
- **Conditional breakpoints** — `add_breakpoint` accepts `condition`, passed to GDB as its native `if` clause so the CPU is only halted when it holds. A VS Code-side condition would still stop the core on every hit and decide afterwards. Conditions, log messages, hit counts and disabled state are surfaced in `list_breakpoints` and the debug state as `file:line [when: ...]`.
- **`list_variable_names` tool** — names and types of everything in scope, reading no values. On a slow probe or a large frame that turns thirty round trips into one.
- **`variableNames` filter** on `get_variables_values` and `get_frame_variables` — read only what you asked for. Names are matched against the DAP `evaluateName` first and then the display name, with an adapter type decoration (`config [Dictionary]`) stripped from both; matching the raw display name alone leaves those variables unreachable. Requested names that match nothing are reported back rather than silently omitted. **Deliberately optional, unlike upstream**, which made it required in 2.3.0 — embedded frames are small, so the full dump is usually what you want, and making it mandatory would break every existing agent prompt for no gain.
- **Secret redaction** (`cmsis-debugmcp.redactSecrets`, default on) — values whose name or content looks like a credential are withheld before leaving the extension, on the variable views and `evaluate_expression`. Two fork-specific carve-outs, because the upstream name-only policy misfires badly on firmware: **numeric scalars are never withheld** whatever the variable is called (a `uint8_t auth`, a `token` counter and `0xDEADBEEF` all stay readable — a 32-bit integer cannot carry a credential), and **raw target reads bypass redaction entirely** (`read_memory`, `read_core_registers`, `read_peripheral_register`, `get_fault_info`, and `-exec` GDB passthrough). Real SVDs name registers `KEY`, `KR`, `KEYR` and `UNLOCK` — the watchdog and flash unlock registers — and those are exactly what you need when the watchdog is resetting you. Strings, buffers and structures still get the full treatment.
- **Multi-window routing.** External agents get exactly one MCP URL, and until now every window ran its own server on whatever port it could get while `agentConfigurationManager` wrote whichever port that window received — so the last window to start won and the agent routinely drove a window that did not hold the board. Now one window binds the well-known port and forwards each call to the window that owns the target, over a token-gated loopback control server, using a shared file registry of live windows. Upstream routes on a file path alone, which suffices there because every one of its tools takes one; only four do here, so the resolution ladder continues past the path: an explicit pin, the session's established target, the sole window with an active debug session (the normal one-window-one-board case), then the sole window. Ties resolve to an error naming every candidate rather than a guess — reading the wrong board's memory reads as a firmware bug and costs far more than being asked to pick.
- **`list_debug_windows` and `select_debug_window` tools** — see the candidate windows and pin one for the session. Registered only when the server is actually routing.
- **Roo Code and Antigravity** added to the agent registration roster, and the selection popup is suppressed under Antigravity/Gemini, which configure MCP servers themselves.
- **`cmsis-debug-live` Agent Skill**, installed to `~/.agents/skills/` (and `~/.copilot/skills/` when present) on agent registration. Written for Cortex-M rather than adapted from upstream's host-process `debug-live`: target awareness from the CMSIS YAMLs, the five-state session gate, the FPB budget, what to do when a variable and the peripheral disagree, fault decode, and the routing tools. Named `cmsis-debug-live` so it cannot collide with upstream's skill when both extensions are installed.

### Changed — upstream sync
- **`add_breakpoint` takes a 1-based `line`.** It previously took a `lineContent` substring and set a breakpoint on *every* line containing it — in C routinely dozens (`}`, `return;`, `break;`), quietly exhausting the FPB comparators. `lineContent` remains as a deprecated optional fallback so existing agent prompts keep working, and the response says when it was used and how many lines matched.
- **MCP transport is per-session rather than per-request.** `initialize` mints an `mcp-session-id` and that session's transport serves its POSTs, its `GET` SSE stream and its `DELETE`. This is not a return to the shared-server bug that hung `get_threads` after three calls — that was one `McpServer` being closed and reconnected per request; a session-scoped server is never closed mid-flight, and `test/transport/session-lifecycle.js` asserts exactly that.
- **The MCP server no longer falls back to an OS-assigned port.** That fallback is what produced the misrouting. Losing the bind now means another window is the router, and this window becomes a worker; workers retry every 10s so closing the router promotes a survivor rather than leaving the agents' URL dead. Every window advertises the router's endpoint, including through the `McpServerDefinitionProvider`, so in-window Copilot routes exactly like an external agent.
- `deactivate()` is awaited, so a window leaves the shared registry before its extension host goes away.

### Fixed — upstream sync
- **The reported current line was read from the active text editor.** VS Code moves the editor cursor asynchronously after a stop and only for the focused editor, so the position lagged the actual stop and was simply wrong whenever focus was elsewhere — and on a `gdbtarget` session the editor may not track the target at all. It now comes from the DAP top stack frame, which is ground truth. This also removed the 300 ms settle sleep that existed only to let the cursor catch up. (Upstream PR #96.)
- **`GET /mcp` returned a bare 404.** Only `POST` was registered, so the server→client SSE stream a client opens right after `initialize` failed. Cursor's MCP client treats that as a fatal transport error and tombstones the connection as "errored" even while POST tool calls keep working. `GET` and `DELETE` are now registered at startup. (Upstream PR #96.)

### Internal
- Removed `waitForStateChange`/`hasStateChanged`, the old 1 s blind-poll loop, dead since stepping moved to the event-driven wait.
- Op dispatch across windows goes through one shared table checked against `IDebuggingHandler` and `SerialHandler` **at compile time**, so adding a tool without making it routable fails the build. Upstream hand-writes two switches; with 31 debug ops and 11 serial ops here, duplicating the list would guarantee drift, and an op that fell out would run in the router window against the wrong board.
- `test/transport/` — two harnesses that drive the real server over a real socket outside the extension host: the Streamable-HTTP session lifecycle (including the three-consecutive-`get_threads` regression gate) and two-window election, publication, pinning and router failover.
- 132 unit tests, up from 6.

### Not taken from upstream
- **The breaking `get_variables_values`** (required `variableNames`) — added as an optional filter instead.
- **`src/utils/withTimeout.ts`** — the fork's `src/utils/timeout.ts` is a superset (`customRequestWithTimeout`, `HardwareTimeoutError`).
- **`debugTestAtCursor` / VS Code Testing API test debugging** — no meaning for `gdbtarget` firmware.

### Security
- **MCP server now binds the loopback interface only.** `app.listen(port)` without a host binds `0.0.0.0`, so the server — which exposes flash download, erase, memory reads, and arbitrary GDB expression evaluation without authentication — was reachable from the local network, contradicting the README's "runs 100% locally". Both the preferred-port and the OS-assigned-fallback listeners now bind `127.0.0.1`. VS Code Remote / WSL port forwarding is unaffected (it forwards localhost).
- **DNS-rebinding protection.** Requests whose `Host` header (or `Origin`, when present) is not a loopback address are rejected with 403. Without this, a malicious web page could point its own DNS name at `127.0.0.1` and drive the debugger through the victim's browser — loopback binding alone does not stop that.

### Fixed
- **Port fallback silently pointed a second VS Code window at the first window's debug server (the port-allocation bug).** `listenWithFallback()` used the `app.listen(port, host, callback)` callback as its success signal, but in Express 5 that callback is invoked unconditionally — *before* the bind result is known. On `EADDRINUSE` it fired with `server.address() === null`, the promise resolved with the dead, unbound server, and the `EADDRINUSE` handler's fallback listener resolved nothing and was leaked. `getActualPort()` then fell back to the *configured* port (3001) — the one already owned by the first window. Consequences: the second window reported "server running on :3001", registered `:3001` with Copilot and wrote it into every agent config, and its agent then drove the **first window's debug session and hardware target** — while the second window's own server accepted no connections at all. Bind success is now taken from the server's `listening` event, the port is read back from the bound socket, and `start()` fails loudly rather than guessing a port.
- A persistent `error` listener is now attached to the running HTTP server; previously a post-startup socket error would have been an unhandled `error` event and taken down the extension host.
- `stop()` clears the cached port so a stopped server can no longer report a live endpoint.
- Changing `cmsis-debugmcp.serverPort` now prompts to reload the window. Previously the setting silently had no effect until the next reload, while agent configs kept pointing at the old port.
- **Spurious "Migrated N agent configuration(s)" toast on every activation.** The migration check treated any `type: 'http'` entry as legacy, but `http` is the *correct* transport for GitHub Copilot CLI (and now Claude Code) — those entries were rewritten and re-announced on every startup. Migration now only fires when the existing transport differs from the one the agent should use.
- **Config files are never clobbered on parse failure.** Previously an unparseable agent config was silently replaced with a fresh object — catastrophic for `~/.claude.json`, which holds session history and settings beyond MCP entries. Configuration now aborts with an error message instead. All config writes go through a temp-file + rename so a crash mid-write can't truncate the file.
- **Stale endpoint refresh.** When the server starts on an OS-assigned fallback port, existing agent config entries pointing at the old port are silently updated on activation instead of being left dead.
- Removed dead code left over from the pre-stateless transport design (`isServerRunning()`, the unused `transports` map) and consolidated the four hardcoded version strings onto `SERVER_VERSION`.
- Packaged `.vsix` shrinks from 29.5 MB to 14.6 MB — the 15 MB demo video was being shipped to every user despite being referenced only from the GitHub repo.

## [1.1.9] - 2026-05-19

### Fixed
- **`cmsis_action attach` false success — real fix (bug #3, third attempt).** Previous attempts probed `getSessionStatus()`, whose DAP `threads` ping is *answered by the adapter process* even when GDB is not connected to a target — a zombie `gdbtarget` session (adapter alive, no target behind the port) kept its VS Code session object and answered the ping for several seconds, so both probes read a phantom `running`. ## [1.1.8] - 2026-05-19

### Fixed
- **False-negative breakpoint warnings.** `add_breakpoint` and `clear_all_breakpoints` printed scary warnings ("⚠️ GDB did not confirm binding", "GDB delete failed") for operations that actually succeeded. Two causes: (1) the DAP `evaluate` of an `-exec break`/`delete` is not a reliable success signal — the `gdbtarget` adapter runs the command (breakpoint binds / delete happens) but frequently returns an empty or error `evaluate` response because it has no scalar result to hand back; (2) `clear`/`clearAll` issued the evaluate with no `frameId`, which the adapter rejects ("Evaluation of expression without frameId is not supported") even though the command still ran. Fixes: a shared `execGdbCommand()` helper now always supplies a `frameId` and never throws on an evaluate error; replies are classified `bound` / `rejected` / `unconfirmed`, and only a *definite* GDB rejection ("No source file", "No symbol", …) produces a warning. A missing echo is reported neutrally — "set; verify with continue_execution" — not as a failure.

## [1.1.7] - 2026-05-19

### Fixed
- **`cmsis_action attach` false "up and stable" (bug #3, second attempt).** The v1.1.6 fix probed `getSessionStatus()` once after a 3 s wait — but a `gdbtarget` session with no GDB server behind the port keeps its *adapter process* alive answering a shallow DAP `threads` ping for a few seconds before collapsing, so a single probe still caught it in the alive window and the "and stable" wording then positively asserted a stability that was false. Now `confirmSessionSurvives()` probes at **two** time points (t+3 s and t+6 s); each requires the session object to still exist *and* `getSessionStatus()` to be `running`/`stopped`. A no-target session has collapsed to `no-session` by the second probe, so it is correctly reported as "did not survive the initial connect", with guidance to start a GDB server or use `load_and_debug`.

### Fixed

## [1.0.27] - 2026-05-18

First public release of the fork. Rolls up the work between v1.0.9 (initial CMSIS fork tag) and v1.0.27 into one release. Published as a GitHub release with `cmsis-debugmcp-1.0.27.vsix` attached.

### Added — CMSIS-Solution-driven workflow
- **`cmsis_action` MCP tool**: wraps the CMSIS Solution panel buttons. Actions: `build`, `load`, `erase`, `load_and_run`, `load_and_debug`, `attach`, `detach`, `stop_run`. **Preferred entry point for Cortex-M debug** over `start_debugging` — `load_and_debug` builds (if needed), flashes the device, and attaches the debugger in one step, matching the panel's "Debug" button. `load_and_debug` and `attach` wait for the session to be usable before returning.
- **Pre-check refusal on duplicate session**: `start_debugging`, `cmsis_action load_and_debug`, and `cmsis_action attach` now refuse with a structured message when a debug session is already active, naming the existing session and pointing the agent at `stop_debugging` / `restart_debugging`.
- **`start_debugging` re-scoped**: tool description rewritten to flag it as **non-CMSIS only** (Python / Java / JS / etc.). For CMSIS projects, `cmsis_action load_and_debug` is the right call.

### Added — Pause, call-stack, threads, frame variables
- **`pause_execution` MCP tool**: DAP `pause` for inspecting a running target without ending the session. State-aware: no-op if already stopped, refuses if probe is unresponsive.
- **`get_call_stack` MCP tool**: full DAP `stackTrace` with frame IDs (up to 200 levels). Agent can walk the stack and pass `frameId` to `get_frame_variables`.
- **`get_threads` MCP tool**: DAP `threads` enumeration. With RTOS-aware GDB servers (pyOCD `--rtos`, J-Link RTOS plugin), FreeRTOS / RTX / ThreadX tasks appear as threads — matching the xRTOS viewer task list.
- **`get_frame_variables` MCP tool**: inspect variables at an explicit `frameId` without changing the editor's active frame. Lets the agent walk up the call stack and examine caller-frame state.

### Added — Per-call timeouts and auto-heal
- **`timeoutMs` parameter on every hardware-touching tool**: agent-supplied deadline, server-capped to 60 000 ms regardless of input.
- **Handler-level `withHandlerTimeout` race**: every inspection tool is wrapped in an outer Promise.race so it always returns within the cap, even if the DAP layer hangs. On overshoot, returns a structured "did not complete within N ms" message with diagnostic guidance.
- **Auto-heal on motion timeout**: `continue_execution` / `step_*` automatically pause the running target on overshoot, read the PC + active frame via `read_core_registers`, and append a 🩹 Recovery section to the response — the agent knows where the firmware actually was instead of seeing a silent "still running".

### Added — Dual serial backend
- **OWNED port** via `serialport` package: `serial_open` / `serial_close` / `serial_write` / `serial_read` (from `'owned'`) / `serial_clear_buffer` / `serial_list_ports` / `serial_status`. MCP server holds the connection and buffers RX up to 1 MB. Use when no MS Serial Monitor UI session is active on the same tty.
- **MS Serial Monitor BRIDGE**: `serial_subscribe_monitor` / `serial_unsubscribe_monitor` runtime-probe `ms-vscode.vscode-serial-monitor` exports for any of `onDidReceiveData` / `onDataReceived` / `onData` / `onSerialData` / `onDidReadData` / `subscribeData`. Today the public API (v0.1.7) only exposes port enumeration; the bridge falls back with a clear "data event not available" message. Auto-lights-up when MS ships a data event — no rebuild needed.
- **`serial_status`**: reports both backends side-by-side and lists the discovered `ext.exports` keys so the agent can confirm what the installed Serial Monitor build exposes.
- **`serial_open_monitor`**: focuses the MS Serial Monitor panel for the user (does not open or read a port). Uses the correct view container ID `vscode-serial-monitor-tools`.

### Added — Stateless HTTP transport (concurrency fix)
- **Per-request `McpServer` instances**: the previous shared-server pattern (`close()` → `connect(newTransport)` on every POST) raced when two tool calls landed concurrently — request B's `close()` stripped the transport request A was about to respond on, hanging request A forever. Now each POST to `/mcp` constructs its own `McpServer` + transport pair and registers tools fresh, matching the official MCP stateless example. Eliminates the `get_threads`-after-three-calls hang.

### Added — Hardware-connection robustness
- **DAP-event-driven session state**: a global `DebugAdapterTrackerFactory` records `stopped` and `continued` events per session. `hasActiveSession()` and `get_session_status` consult this tracker instead of `vscode.debug.activeStackItem`, which is `undefined` whenever the CPU is running and during the brief race window right after a stop event. Eliminates spurious "session is not ready" / "no debug session" reports while the target is just running.
- **`get_session_status` MCP tool**: never-failing classification of the session into `no-session` / `initializing` / `running` / `stopped` / `unresponsive`, with a hint about what to do next.
- **State-aware inspection errors**: inspection tools (`get_variables_values`, `evaluate_expression`, `read_memory`, `read_core_registers`, `read_peripheral_register`, `get_fault_info`) route through `ensureStoppedSession` and report the actual session state ("running — add a breakpoint", "unresponsive — call check_target_connection") instead of a misleading "no debug session".
- **Per-DAP-request timeouts**: every `customRequest` to the debug adapter is wrapped with a deadline. A stalled probe cannot hang an MCP tool call indefinitely.
- **`HardwareTimeoutError`**: dedicated error type with actionable message.
- **`check_target_connection` MCP tool**: low-cost DAP `threads` ping with a short internal timeout. Diagnostic-grade liveness check.
- **`hasDebugSession()` / `hasActiveSession()` split**: synchronous session-existence check (for `stop_debugging` / `restart_debugging`, works even when target is running) vs. async stopped-frame check (for inspection tools).
- **Parallel core-register reads**: `read_core_registers` issues all 23 evaluates concurrently with per-request and overall deadlines. Individual register failures report `<timeout>` / `<unavailable>` instead of bringing down the whole call.
- **Bounded `read_memory`** and **`read_peripheral_register`**: total time per call capped by `memoryReadTimeoutMs`.
- **`restart_debugging` actually waits** for the session to become ready again, rather than returning after a fixed 300 ms delay.
- **`step_*` / `continue_execution` surface timeouts and session loss**: results annotate when the target failed to stop within the timeout or when the session terminated mid-operation, instead of silently returning a stale state.

### Added — Agent guidance (`debug_instructions.md`)
- **PHASE 0 — Target awareness**: agent reads `<name>.cbuild-idx.yml` → `<context>.cbuild.yml` → `<context>.cbuild-run.yml` → `.vscode/launch.json` before any debug call, and asks the user to regenerate `launch.json` via **Manage Solution → Debugger** if missing. Pointers to CMSIS-Pack documentation links from the CMSIS Solution dialog.
- **PHASE 1 — Session status gate**: 5-state decision table for `get_session_status`, telling the agent the correct next action for each (`no-session` → `cmsis_action load_and_debug`; `running` → pause first; `unresponsive` → `check_target_connection`).
- **Cortex-M hardware breakpoint limit**: documents the FPB comparator ceiling (M0/M0+/M23: 4, M3/M4: 6, M7/M33/M55/M85: 8) and recommends `list_breakpoints` before adding, iterative replacement, and `clear_all_breakpoints` between phases.

### Added — Real-board test driver
- **`test/realboard/run.ts`**: end-to-end test runner that connects to the running MCP server (Streamable HTTP) and exercises every tool. Pre-flight `estimatedMs` per test; hard timeout `min(2 × estimatedMs, 60 s)`; pauses and runs a diagnostic sweep (`get_session_status` / `check_target_connection` / `get_fault_info`) on every overshoot. Board-specific knobs (endpoint, configurationName, ELF region, peripheral name, serial path) come from `realboard.config.json`.

### Configuration
- **`cmsis-debugmcp.dapRequestTimeoutMs`** (default 10000) — per-request DAP timeout.
- **`cmsis-debugmcp.memoryReadTimeoutMs`** (default 30000) — overall cap for `read_memory` / `read_core_registers`.

- **Static `mcp.json` write for GitHub Copilot**: superseded by the `vscode.lm.registerMcpServerDefinitionProvider` registration done at extension activation, which eliminates the startup race condition and handles dynamic port assignment automatically.

# Documentation and build-artefact tools (`packDocs`, `buildInfo`)

Merged from the experimental CMSIS Pack Docs extension. Two pure cores, two
handlers, one dispatch seam, wired into the MCP server and the multi-window
router the same way as the serial tool group. The [knowledge tools](knowledge.md)
share their dispatch and host but have their own handler and are always enabled.

Two working notes under `docs/proposals/` go further than this page: the
[cross-extension call inventory](../proposals/extension-calls.md) lists the
exact calls into other extensions, and the
[document-storage proposal](../proposals/pack-docs-storage.md) separates the
existing storage functions from a proposed provider API, with
[Pack Docs storage at a glance](../proposals/pack-docs-storage-overview.md)
as its one-page map.

## Wiring

- **Op table** (`src/core/opTable.ts`): `PACKDOCS_DOC_OPS` (5) and `PACKDOCS_BUILD_OPS` (5) form `PACKDOCS_OPS`; the shared dispatch also includes `KNOWLEDGE_OPS` (3). `isPackDocsOp`, `isKnowledgeOp` and `isPackDocsDocOp` select the handler. The five documentation ops are `SLOW_OPS` (10-minute router floor). Compile-time coverage checks the op lists against the handlers' `handle*` methods.
- **Every window** builds the documentation, build and knowledge handlers at activation (`extension.ts` → `createPackDocsHandlers`) — they do nothing until called — and hands them to its `ControlServer`, so a forwarded op executes in the window that owns the workspace. The op table selects the serial, documentation, build, knowledge or debugging handler.
- **Downloads** of `fetch_doc` are jobs of the handler, one per document id (`startDownload()` in `src/packDocsHandler.ts`): up to 10 minutes whatever the call waits, so a client that gives up after 60 s no longer ends them. A call waits until shortly before its deadline, then answers `running` with the bytes received (`renderDownloadRunning()`); a later call joins the same download and indexes the PDF once it is in. A failure is kept until a download succeeds: the next call reports it if no reply has, and from the second failed attempt on the reply sends the user to the workspace docs folder instead. `dispose()` aborts what runs (`ResolveContext.signal`); `downloadPdf()` reports progress through `ResolveContext.onProgress`.
- **Router**: `RoutingDebuggingHandler.packDocsOp` forwards like `serialOp`; `WindowCoordinator.sessionHandlers()` returns `packDocs: (op, args) => router.packDocsOp(op, args)`. Documentation and build calls resolve through the pinned / cached / sole-window rungs. Knowledge calls can fall back to the router's window, and `knowledge_search` accepts a `window` argument for its project context; see [windowRouting.md](windowRouting.md#choosing-the-target-window).
- **Gates**: `DebugMCPServerOptions.packDocsEnabled` and `buildInfoEnabled` (default `false` in the options; the settings `packDocs.enabled` and `buildInfo.enabled` are on by default since 2.5.3), fixed per server instance; `registerTools()` registers those two groups only when their gate is on and the session has a dispatch. The MCP `instructions` describe each enabled group and name the setting for a disabled one. Knowledge has no gate: its tools are registered whenever the dispatch exists. The bare single-window `DebugMCPServer` default (tests) has no dispatch and registers none of these three groups.

## The target and its packs

`resolveTarget` (`targetDocs.ts`) asks before it guesses. Explicit arguments
come first. Without a `target`, `cbuildRunFile` or `pack` it takes the
cbuild-run file of the CMSIS Solution extension's active target
(`PackDocsHost.activeCbuildRunFile`, the extension's `getCbuildRunFile`)
when that file exists and names a device-pack; otherwise it scans the
workspace and narrows by `target` and the active context, as before.

A pack is looked for first in the folder the extension names for the active
target's DFP or BSP (`activePackFolders`: `getDfpPath`, `getBspPath`), and
that folder counts only when its PDSC declares the pack (`holdsPack` in
`pdscBooks.ts`). It may lie outside the pack root, which is how a pack a
csolution names with `path:` is found; a relative answer is resolved against
the folders of the target's cbuild.yml files. The resolution carries the
folders as `packDirs`, and `locatePack` takes them before the pack root,
where another installed version stands in for a missing one and the note
says so. The VS Code host asks through `src/utils/solutionQueries.ts`: only
while the extension is active (asking would activate it), each command
feature-detected, 3 s per answer; `src/core/solutionAnswers.ts` interprets
the answers (`""` and `"<not found>"` are none) for every caller of the
extension's getters.

## Extraction and ranking

- **Extractor** (`pdfExtract.ts`): `PdfjsExtractor` is the bundled default (`packDocs.extractor: auto`/`pdfjs`) — pdf.js legacy build, loaded on first use with a dynamic import; lines are rebuilt from text items by baseline and wide gaps become double spaces so table columns survive. The library runs on a `worker_threads` worker of its own (`pdfWorker.ts`, bundled by esbuild as `dist/pdfWorker.js` beside `extension.js`): pdf.js refuses to start when `Array.prototype` or `Object.prototype` has an enumerable property, and the extension host is shared with extensions that patch them (the CMSIS csolution extension assigns `Array.prototype.groupedBy`) — a worker thread is a fresh realm. `PdfjsExtractor` posts a file path and gets the page texts back; the thread is kept for the next document, retired after a minute idle, and terminated when an extraction times out. Inside the thread pdf.js does not detect Node (Electron), so `GlobalWorkerOptions.workerSrc` points at the shipped `node_modules/pdfjs-dist/legacy/build/pdf.worker.min.mjs` (re-included by `.vscodeignore`), imported there as a fake worker. `itemsToPageText` lives in `pdfText.ts`, shared by the worker and the tests. `PdftotextExtractor` (poppler) stays selectable; a document extracted by the other extractor is re-extracted on its next use so text sources never mix.
- **Tokenizer** (`tokenizer.ts`): NFKC before tokenising, identifier expansion (`RCC_AHB2ENR1` → `rcc`, `ahb2enr1`), hex spellings folded.
- **Index** (`bm25Index.ts`, version 2): body postings plus heading postings per page; BM25 over the body plus `headingWeight` (5) × the heading term score; a version-1 index on disk is rebuilt from `pages.jsonl` on first load. `search.ts` adds phrase, manual and table-of-contents adjustments and a 1.5 heading tie-breaker.
- **Query expansion** (`queryExpansion.ts`): identifier-only queries are expanded from the device SVD at half weight — a peripheral instance with its type synonyms and description, a bare field name with its register and description. Register names, prose and quoted phrases are not expanded (measured: it only dilutes). Expansions never gate the all-terms boost.
- **Benchmark** (`scripts/search-benchmark.ts`, `npm run bench:search`): gold pages are the manual headings that name a register, queries come from the SVD descriptions; reports R@1 / R@3 / MRR per heading weight and post boost, and can extract a PDF with either extractor first. Numbers in `docs/improvement-notes.md` §11.

## Storage

Extracted page text, metadata and indexes live under `<globalStorageUri>/packdocs/` — `<vendor>/<pack>/<version>/<slug>.{pages.jsonl,meta.json,idx.json}` for pack documents, `workspace/<hash>/…`, `user/<hash>/…`, `web|arm/<id>/…` for fetched ones. User-document ids carry their scope folder (`user/keil/stm32u5xx-dfp/rm0456`; `user/<name>` at the root), so a file name repeated in two scopes never collides. PDFs themselves stay where they are. The user documents folder defaults to `~/.cmsis-pack-docs/user` so documents imported with the standalone extension stay attributed.
